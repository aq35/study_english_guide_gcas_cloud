# 補章: セキュリティ(AWS編)を読む

出典: [GCASガイド「セキュリティ(AWS編)」](https://guide.gcas.cloud.go.jp/aws)と、親にあたる[「利用システムが考慮すべきセキュリティ(共通)」](https://guide.gcas.cloud.go.jp/general)
英訳は筆者の訳。カタカナの `/` は息継ぎ(ルールは [linking-rules.md](../linking-rules.md))。
「ガイド:」はGCASガイドに書かれていること、「推論:」は筆者の推論。
**注意**: 認証方式などは、読んだ時点(2026年10月)の記述。「令和7年度以降に禁止予定」のように、時期が書かれている項目は、最新の状況を確認すること。

## 1. 全体像

- ガイド: オンプレミスは**境界型**(外から内への侵入を防ぐ)が主流。クラウドは外と内の境界があいまいなので、**ゼロトラスト**(すべてのアクセスを信用しない)が前提。ただし、インターネットとVPCの境界など、重要なポイントには、境界型の対策も行う。
- ガイド: 責任は3つに分かれる(利用システム、ガバメントクラウド管理組織、CSP)。このガイドが扱うのは、**利用システム側**のセキュリティ。
- ガイド: 利用システムのセキュリティは、3つで構成される。
  1. ガイドに基づくシステム構成と運用で実現するセキュリティ
  2. テンプレート/IaCファイルを使って構築することで実現されるセキュリティ
  3. 払い出し時に自動的に設定される予防的・発見的統制

## 2. やったほうがいい / やめとけ(まとめ)

| やったほうがいい | やめとけ |
|---|---|
| EC2を使わず、マネージドサービスを使う(OS・ミドルウェアが責任範囲外になる。マルウェア対策・脆弱性対策で、最も効果的) | EC2にこだわって、OSの対策を抱え込む |
| MFAを全員に。管理者・本番相当環境は、FIDO準拠のハードウェアトークン | ID・パスワードだけの認証。パスキー、SMS認証(令和7年度以降に禁止予定) |
| 保管データは、利用システム側で管理する暗号鍵(カスタマーマネージドキー)で暗号化 | S3やRDSの既定の暗号化に任せきりにする(AWS所有のキーなので、鍵の管理や確認ができない) |
| シークレットは Secrets Manager で管理 | シークレットを、コードや環境変数に保存する |
| 通信は、HTTPSなど暗号化されたものに限定する(CloudFrontで、TLS 1.2 の新しい方のポリシー) | HTTP、FTPなど、暗号化されていない通信 |
| WAFの新しいルールは、まず**カウントルール**で試す | 新しいルールを、いきなり拒否ルールで適用して、正常な通信まで止める |
| Security Group と NACL の**両方**で二段防御 | どちらか1つだけで済ませる(1つで足りる場合でも) |
| インターネットに接続するシステムは、Shield Advanced の保護対象とSRTサポートを設定する | インターネットに接続しないシステムで、Shield Advanced を有効化する |
| 開発環境と本番環境で、最小権限の粒度を変える | すべての環境で、アクション単位の最小権限にこだわって、運用が破綻する |
| コードのマージは、プルリクエストとレビュアーの承認を経る | 開発者の独断でマージする |
| Inspector は、ECRで**拡張スキャン**にする | 既定の基本スキャンのまま(OSだけで、言語パッケージはスキャンされない) |
| アプリケーションログは、必ず保存する | ログを不要に長期間保存する |
| 「セキュリティに関する連絡先」にメールアドレスを登録する | 登録しないまま、不正使用報告を見逃す |

## 3. 領域ごとの要点(AWS編)

### 認証(MFA)

| 対象 | 方式(ガイド) |
|---|---|
| ①管理者権限のユーザー、または本番相当環境(本番、共通運用管理、CI/CD)にアクセスするユーザー | ID・パスワード + **FIDO準拠のハードウェアMFAトークン**(FIDO U2F / FIDO2) |
| ②それ以外のユーザー | ID・パスワード + 次のいずれか: セキュリティキー / 認証システムアプリ / Googleからのメッセージ |

- ガイド: **パスキーは許可していない**。SMS認証は、令和7年度以降に禁止予定。
- ガイド: 調達で選べるなら、将来の互換性のために FIDO2 対応のトークンを選ぶ。特権管理者(AWSのルートユーザーなど)のトークンは、**金庫など施錠できる場所に保管**する。
- ガイド: ハードウェアのワンタイムパスワード(TOTP)トークンは、GCASの認証では使えない。AWS環境のルートユーザーやIAMユーザーの認証は、GCASと直接連携しないので使える。

### 接続元の制御(管理コンソール)

- ガイド: ガバメントクラウドでは、全ユーザーが IAM Identity Center(IdC)のポータル経由で、マネジメントコンソールに入る。IdCユーザーのIPアドレス制限はIdCの管理者権限が必要で、利用組織には開放していない。そのため、**IdCユーザーの接続元制限には、Chrome Enterprise Premium(CEP)を使う**(端末シリアル番号またはIPアドレス)。
- ガイド: 利用システムが作ったIAMロールへのスイッチロールは、信頼ポリシーの Condition に `IpAddress`(`aws:SourceIp`)で、許可するIPを指定できる。ただし、IdCからのログイン自体には効かない。**CLIの利用時は、アクセス制御が適用されない**ので注意する。
- ガイド: 方針は組織で違う。府省庁、独立行政法人等、公共SaaS事業者は**オプション**。地方公共団体等は、本番相当環境で「接続元端末制限」が**必須**(総務省のガイドラインに基づく)。

### 最小権限の使い分け(環境別)

| 環境・業務 | 最小権限へのアプローチ | 発見的統制による補完 |
|---|---|---|
| 開発環境 | セキュリティやネットワーク設定を変えるなどの特定の操作**以外**を許可する(MFAやログ取得の仕組みを変えられないようにする) | GuardDuty による監視 |
| 本番: 定型運用(監視、バックアップなど) | **アクション単位**で許可。事前に管理者が承認したコマンドだけ | GuardDuty による監視、サンプリング点検 |
| 本番: 非定型運用(システム変更、トラブルシューティング) | **時限的**なIAMロールの払い出しや、アクセスレベル(List、Read、Write)単位の権限 | GuardDuty による監視、申請内容とのずれの確認、操作内容の全量点検 |

- ガイド: アクション単位の最小権限は、厳密にできる反面、設計と運用の負荷が著しく高くなる場合がある。だから、環境と使い方に応じて、**メリハリをつける**。開発環境は、保護すべきデータがない構成にして、試行錯誤できるようにする。
- ガイド: 権限の与え方は2つ。**アイデンティティベース**(ユーザーなどの主体にIAMポリシー)と、**リソースベース**(S3のバケットポリシーなど、リソースに直接ポリシー)。

### 通信と暗号化、シークレット

- ガイド: Webアプリは、前段に **CloudFront** を置き、通信をHTTPSに制限する。CloudFrontはWAFを使え、CDNなのでDDoS対策も兼ねる。セキュリティポリシーは **TLSv1.2_2018 以上**、新しいほど安全なので最新の **TLSv1.2_2021** を推奨。ALBでも同じ基準。
- ガイド: S3へのアクセスは、署名付きURLを使い、**Origin Access Control(OAC)**で、CloudFrontからのアクセスだけを許可する構成が図で示される。
- ガイド: ファイル転送は、**Transfer Family** で、マネージドのSFTP/FTPSサーバを構築できる。
- ガイド: **KMS**: 利用システム側が管理できる**カスタマーマネージドキー**を強く推奨。AWSマネージドキーは、ローテーションやキーポリシーの編集ができない。AWS所有のキーは、管理も確認もできない。**S3は既定で暗号化されるが、AWS所有のキーなので、鍵の選択に留意する**。RDSも、マネジメントコンソールからの利用時の既定の暗号化は同様。EBSにも留意する。
- ガイド: 共通編の補足: 暗号鍵を自分たちで管理していると、利用終了時に「暗号化消去」(鍵を消して、データを読めなくする)ができる。
- ガイド: **Secrets Manager**: DBの認証情報、APIキーなどを管理・ローテーションする。KMSと統合され、暗号化して保存する。シークレットを**コードや環境変数に保存しない**。
- ガイド(共通編): HTTPS用のサーバ証明書は、自動更新サービスが正しく動かず、期限切れでアクセス不能になる事例がある。自動更新を使うなら、**正しく動くことを確認して**運用する。

### WAF、ファイアウォール、DDoS

- ガイド: WAFのルールは、AWSマネージドルール(OWASPやCVEなど、一般的な攻撃を防ぐ)と、カスタムルールの2種類。**マネージドルールに加えて、カスタムルールの継続的な更新**を推奨。
- ガイド: 新しいルールは、**カウントルール**で適用すると、通信に影響を与えずに、当てはまる通信の数を測れる。
- ガイド: ファイアウォールは3種類。

| 名称 | 特徴 |
|---|---|
| Security Group | VPC上のリソースに適用。ステートフル。料金なし |
| NACL | サブネットに適用。ステートレス。料金なし |
| AWS Network Firewall | InternetGatewayを通る通信を、プロトコル、IP、ドメインなどで許可・ブロック。料金あり |

- ガイド: SGとNACLで、必要なIPレンジとポートだけ開放する。**両方で二段防御**を推奨。送信先ドメインの制限など、SGとNACLで満たせない要件があるときに、Network Firewall が効果的。
- ガイド: **Shield Standard** は、すべてのアカウントで自動的に有効。**Shield Advanced** は、ガバメントクラウドでは有効化されている。ただし、機能させるには保護リソースの設定が必要。インターネットに接続し、保護対象のリソースを使うシステムは、設定する。**SRTサポートも有効化**する。インターネットに接続しないシステムでは不要なので、むやみに有効化しない。

### マルウェア対策、脆弱性対策

- ガイド: どちらも、**最も効果的なのは、EC2を使わず、マネージドサービスでOSを責任範囲外にすること**。
- ガイド: **GuardDuty**: 脅威を検知する(機械学習)。**検出のみで、駆除はしない**ので、検出されたらファイル削除などの対処をする。環境の払い出し時に有効化されている。
- ガイド: **Inspector**: EC2とECRのイメージの脆弱性をスキャン。ECRは**既定の基本スキャンが、OSだけで言語パッケージを見ない**ので、拡張スキャンに変更する。EC2を使うなら脆弱性対策は必須で、Inspectorを推奨。
- ガイド: **パッチマネージャー**(Systems Manager): OSパッチを自動化。**開発環境でテストしたパッチベースラインと同じ内容を本番に適用**すると、操作ミスが減る。メンテナンスウィンドウで、稼働していない時間に自動適用できる。EC2を使うなら推奨。
- ガイド(共通編): マルウェア対策製品を入れただけで終わりにしない。日常の脆弱性対策と、不審な動きの検知が中心で、製品はその補完。ファイルアップロードを受けるときは、ファイルを直接マネージドストレージに保管すれば、実行されるタイミングがなくなる。

### CI/CD

- ガイド: CodePipelineに付与するIAMロールは、**最小権限**にする。コードのマージは、プルリクエストを作り、レビュアーの承認を得てから。
- ガイド: コンテナは **ECRのイメージスキャン**(拡張スキャンを推奨)。コードの脆弱性は **CodeGuru**。プルリクエストのたびに自動スキャンすると、チェック漏れを防げる。

### ログ、監視、検知

| サービス | ガイドの記述 |
|---|---|
| CloudTrail | AWSアカウントのアクティビティログ。**環境の払い出し時に有効**。ただし**90日間保存で、以降は削除**されるので、必要ならS3に保存する |
| CloudWatch Logs | AWSサービスとアプリのログを集中管理。使えるサービスでは、他の手段がない限り使う。**アプリケーションログは必ず保存**する。ECSは、ログドライバで `awslogs`(簡単、複雑な設定は不可)か `awsfirelens`(転送先の振り分け、加工、Kinesis Data Firehoseへの転送が必要なとき)を選ぶ |
| S3(ログの保存先) | コストは抑えられるが、検索やフィルタが使えない。どちらが適切か検討する。保存期間は、コストとのバランスを考えて、不要に長くしない |
| Detective | セキュリティ検出結果の根本原因の分析・調査(CloudTrailログ、VPCフローログ、GuardDuty、Security Hubの結果などを取り込む) |
| Config | リソース構成の変更を継続的に評価・記録。ルール(Config Rule)で評価。**払い出し時に有効**。ルールの追加は可能 |
| Security Hub | ベンチマークの自動チェック(CIS AWS Foundations Benchmark、AWS 基礎セキュリティのベストプラクティス)。**既定で有効**。検出結果はダッシュボードで確認 |

- ガイド: GuardDuty、CloudTrail、Config、Security Hub は、いずれも払い出し時に有効なので、**導入を検討する必要はない**。
- ガイド: Amazon Fraud Detector は、2024年5月時点で、東京・大阪リージョンでは利用できない。

### 不正使用報告(Abuse Report)への対応

- ガイド: アカウントのリソースがスパム送信、ポートスキャン、DDoS攻撃、マルウェア配布などに使われている疑いがあると、AWS Trust & Safetyチームから、不正使用報告のメール(英文)が来る。
- ガイド: ルートユーザーのメールアドレスはデジタル庁が管理するので、利用システム側で、**「セキュリティに関する連絡先」(代替連絡先)に、メールアドレスを必ず登録**する。
- ガイド: 受信したら、**24時間以内に、メールに直接返信する**(件名は変えない)。初回の返信は、対処の完了まで要らず、「認識して調査を始めた」と伝えるためのもの。**24時間以内に応答しないと、リソースのブロックや、アカウントの一時停止の措置が行われる場合がある**。
- ガイド: 調査の結果、不正行為なら再発防止の措置を返信する。該当しないなら、その旨を回答する。技術的な支援が必要なときは、AWSサポートにケースを起票する。

### CDK(テンプレート/IaC)でのセキュリティ

- ガイド: ガバメントクラウドは、CloudFormationではなく **CDK** を使う。
- ガイド: Constructは L1(CloudFormation相当。詳細な定義が必要)、L2(デフォルトと定型文を内包。必要なプロパティが少ない)、L3(複数を組み合わせたライブラリ。用途が特化)。**抽象化と扱いやすさのバランスが良い L2 を推奨**。高レベルほど、AWSのベストプラクティスを内包するので、セキュリティの欠陥の減少が期待できる。
- ガイド: **cdk-nag** を使うと、Constructがベストプラクティスに準拠しているかをチェックできる。非準拠の内容は、修正するか、理由を書かないとデプロイできない。利用を推奨。

## 4. 払い出し時に、すでに有効なもの(ガイド)

| サービス | 状態 |
|---|---|
| CloudTrail | 有効(ログは90日間) |
| AWS Config | 有効 |
| Amazon GuardDuty | 有効 |
| AWS Security Hub | 有効(CIS、AWS 基礎セキュリティのベストプラクティスの基準) |
| AWS Shield Advanced | 有効化されている(ただし、保護リソースの設定は利用システムが行う) |

## 5. ガイドが書いていないこと

- 個々のIAMポリシーの完全な例(スイッチロールの信頼ポリシーの例だけがある)。
- 各サービスの具体的な設定手順(公式ドキュメントへのリンクで案内される)。
- 推論: 認証方式など、時期が書かれている項目は変わりうる。最新の記述を確認する必要がある。

## 6. 5文で言ってみる

### 1
- **日本語訳**: EC2を使わず、マネージドサービスを使うのが、最も効果的な対策。
- **English**: Using managed services instead of EC2 is the most effective defense.
- **カタカナ**: ユーズィングマニジドサーヴィスィズ / インステッドオヴィーシーツー / イズザモウストイフェクティヴディフェンス

### 2
- **日本語訳**: 管理者には、ハードウェアトークンを使う。
- **English**: Administrators use a hardware token.
- **カタカナ**: アドミニストレイタズユーズアハードウェアトウクン

### 3
- **日本語訳**: 鍵は自分たちで管理する。
- **English**: Manage your own encryption keys.
- **カタカナ**: マニジョアオウンインクリプションキーズ

### 4
- **日本語訳**: 新しいWAFルールは、まず、カウントで試す。
- **English**: Try a new WAF rule in count mode first.
- **カタカナ**: トライアニューワフルール / インカウントモウド / ファースト

### 5
- **日本語訳**: 不正使用報告には、24時間以内に返信する。
- **English**: Reply to an abuse report within 24 hours.

## 語彙

| English | カタカナ | 日本語 | 詳しい説明 |
|---|---|---|---|
| zero trust | ズィーロウトラスト | ゼロトラスト | すべてのアクセスを、内側からでも信用せず、そのつど確認する考え方 |
| MFA (multi-factor authentication) | エムエフエー | 多要素認証 | 知識(パスワード)、所有物(トークン)、生体など、複数の要素を組み合わせる認証 |
| FIDO | ファイドウ | FIDO | パスワードに頼らない認証の国際規格。ハードウェアトークンもこの規格に準拠 |
| customer managed key | カスタマーマニジドキー | カスタマーマネージドキー | 利用者が作成・管理する暗号鍵。ローテーションやアクセス制御ができる |
| cryptographic erasure | クリプトグラフィックイレイジャー | 暗号化消去 | 暗号鍵を消して、データを読めなくすること |
| WAF (web application firewall) | ワフ | WAF | Webアプリへの攻撃を防ぐ仕組み |
| count rule | カウントルール | カウントルール | 通信を止めずに、ルールに当てはまる数だけ数えるルール |
| least privilege | リーストプリヴィリッジ | 最小権限 | 仕事に必要な最小限の権限だけを与えること |
| patch baseline | パッチベースライン | パッチベースライン | どのパッチを適用するかを決めた基準 |
| abuse report | アビューズリポート | 不正使用報告 | リソースが不正な行為に使われている疑いがあると、AWSから届く通知 |
