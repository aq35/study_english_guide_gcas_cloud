## 1. DBは何がいい?

### 結論(ガイドの答え)

- ガイド: 「これ1つ」という推奨はない。**データの種類(用途)で選ぶ**。Rebuildでは「移行するデータベースの種類によりAWSサービスを選択」する。
- ガイド: 既存システムのRDBは、Replatform(R1)では**マネージドの Amazon Aurora / Amazon RDS** にする。DBMSをEC2に自前で入れる構成は、既存DBMSがマネージドサービスに対応していない場合などの**例外**。

### データの種類と、AWSサービス(ガイドの表3)

| データベースの種類 | 特徴 | AWSサービス | 向いている用途(ガイド) |
|---|---|---|---|
| リレーショナル | 参照整合性、ACIDトランザクション | Amazon Aurora / Amazon RDS | ERP、CRM、会計 |
| キーバリュー | 高スループット、低レイテンシ、制限のない拡張性 | Amazon DynamoDB | トラフィックの多いWebアプリ、eコマース、リアルタイム入札 |
| ドキュメント | ドキュメントを格納し、任意の属性で高速にアクセス | Amazon DocumentDB | コンテンツ管理、カタログ、ユーザープロファイル |
| インメモリ | マイクロ秒のレイテンシで、キーで検索 | Amazon ElastiCache / MemoryDB | キャッシュ、セッション管理、ゲームのリーダーボード |
| グラフ | データ同士の関係を、高速に作成・探索 | Amazon Neptune | 不正検出、ソーシャルネットワーク、レコメンド |
| 時系列 | 時間とともに計測されるデータを蓄積・処理 | Amazon Timestream | IoT、イベントトラッキング |
| 台帳 | すべての変更履歴を、不変で検証可能に保持 | Amazon QLDB | 記録システム、サプライチェーン |
| ワイドカラム | スケーラブルで高可用な、Cassandra互換 | Amazon Keyspaces | 低レイテンシのアプリ、Cassandraからの移行 |

注意(ガイド外): 表の Amazon QLDB は、AWSが提供を終了している(下の「ガイド外」を参照)。

### 構成のヒント(ガイド)

| 場面 | ガイドの記述 |
|---|---|
| マイクロサービス | 構成図の例では、コンポーネントごとに**専用のDB**を持つ(分割の基準1) |
| 更新と参照で要件が違う(CQRS) | 実装例: 更新は DynamoDB の非正規化テーブル、参照は Aurora の正規化テーブル(Kinesis Data Streams または DynamoDB Streams と Lambda で同期)。ただし、コマンド側とクエリ側の**結果整合性を許容する**必要がある |
| 有償DBMS(Oracle、SQL Server) | Amazon RDS for Oracle / for SQL Server がある。エディションによっては、AWS上でサポートされないことがある。既存ライセンスを持ち込む **BYOL は原則禁止** |

### 迷ったときの手がかり(推論)

- 推論: 「業務の記録・帳票・会計のように、整合性が大事」→ リレーショナル(Aurora / RDS)。ガイドの用途欄(ERP、CRM、会計)に沿った読み方。
- 推論: 「アクセス数が多く、キーで引く処理が中心」→ DynamoDB。「キャッシュ、セッション」→ ElastiCache。ガイドの用途欄に沿った読み方。
- 推論: AuroraとRDSのどちらにするかは、表3では分けられていない。ガイドのコスト最適化の表に、「可用性や性能が高度に要求されない場合は、Aurora から RDS PostgreSQL/MySQL への乗せ換え」という行があるので、要求が高いほど Aurora、低いほど RDS、という方向に読める。

## 2. DBまわりの「やめとけ」(ガイドのコスト最適化の表)

ガイドは、基準に当てはまる状態を「見直す対象」として挙げる。つまり、そのままだと損、という状態の一覧。

| サービス | やめとけ(基準) | 代わりに(ガイドの対応) |
|---|---|---|
| DynamoDB | 予測できないトラフィックなのに、リザーブドキャパシティやプロビジョニング済みモードを使う | オンデマンドキャパシティを検討する |
| DynamoDB | 予測できるトラフィックなのに、オンデマンドを使う | 過去のトラフィックから、プロビジョニング済みで適切なWCU/RCUを検討する |
| DynamoDB | `Scan` で全件検索して、不要なデータまで取る | GSI/LSI を使って、不要なデータの取り出しを防ぐ |
| DynamoDB | 使っていないGSIを残している | 使っていないGSIを削除する |
| DynamoDB | あまり使わないデータを長く保存している / 削除の運用がない | Standard-Infrequent Access の適用、過去データのS3への退避や削除運用の追加 |
| Aurora | リードレプリカの数を自動調整していない | Aurora のオートスケーリング |
| Aurora | 業務の特性を見て、サーバレスを検討していない | Aurora サーバレスの採用(稼働が少ないノードなど) |
| Aurora | 可用性・性能が高度に要求されないのに Aurora を使う | RDS PostgreSQL / MySQL への乗せ換え |
| RDS | アイドル状態のRDSを動かし続ける | 不要なインスタンスの停止運用 |
| Aurora / RDS | CPUとメモリの使用率が月平均30%以下 | インスタンスタイプの最適化 |
| S3 | 用途にかかわらず、S3 Standard だけを使う | ストレージクラスの最適化、Intelligent-Tiering |

## 3. 「やめとけ」一覧(ガイドが禁止・制限しているもの)

| やめとけ | ガイドの記述 |
|---|---|
| 東京/大阪以外のリージョン | 使用禁止(予防的統制) |
| IAMユーザーの永続的なアクセスキー | 作成禁止。MFAを強制し、権限はIAMロールで管理 |
| Adminユーザー以外のIAM権限付与 | 禁止 |
| AWS Marketplace | 原則禁止。代替できない場合はデジタル庁に相談 |
| AWS Outposts、VMware Cloud on AWS、ROSA | クラウドサービスとしての利用禁止 |
| AWS CloudShell(VPC environment 以外) | 利用禁止 |
| リザーブドインスタンス、Savings Plans など(一度の誤操作で高額請求) | 購入・実行を防止。一部は「長期継続割引購入申請書」で、合理的な理由があれば許可 |
| Bedrock の、デジタル庁が許可していないモデル | 利用禁止 |
| 1つのシステムでの複数CSP | 原則禁止(例外あり) |
| VDI、DaaS、シンクライアント | 原則使用しない(例外あり) |
| BYOL(既存ライセンスの持ち込み) | 原則禁止 |
| 管理コンソールでのインフラ構築・変更 | IaCが原則。コンソールは参照時のみ |
| クラウドの管理画面を、業務アプリの一部として使う | 原則避ける。職務分離や、インフラ構成がリスクにさらされる観点から |
| 特定ベンダーしか使えないCI/CDツール | ベンダーロックインのリスクがあるので控える |
| 監視・ログ・バックアップ・DBを、仮想マシン上に自前で作る | 「作らない」。マネージドサービスで構築する |
| EC2のジョブ管理サーバ | 暫定の例外のみ(次期更改時にマネージド化が必須) |
| 外部のCSPMサービスの安易な導入 | 過剰になりやすい。CSP標準の機能で対応できない要件がある場合に限り検討 |

## 4. ガイド外: 提供終了が発表されているもの(要確認)

ガイドの表に載っていても、AWS側の提供状況が変わっていることがある。次はWeb検索で見つけた情報で、ガイドには書かれていない。最新の状況は、AWSのドキュメントで確認すること。

| サービス | 状況(ガイド外) | 出典 |
|---|---|---|
| Amazon QLDB | サポート終了日は2025年7月31日。AWSは、Amazon Aurora PostgreSQL への移行を案内している、と紹介する記事がある | [QLDB(提供終了)の解説](https://tutorialsdojo.com/tag/amazon-qldb-tutorials/)、[2024年9月頃にサポート終了等が発表されたサービスのまとめ](https://blog.serverworks.co.jp/aws-services-end-of-support-september-2024) |
| AWS App Mesh | サポート終了日は2026年9月30日。2024年9月24日から新規の利用開始ができない。ECS Service Connect への移行を案内している | [AWS App Mesh のドキュメント](https://docs.aws.amazon.com/app-mesh/latest/userguide/appmesh-integrations.html) |
| AWS CodeCommit | 2024年6月6日から、新規のお客様の受付を停止している(既存の利用者を除く) | [Simon Willison のまとめ](https://simonwillison.net/2024/Jul/30/aws-codecommit-quietly-deprecated/) |

ガイドの表(Rebuildの表2)には、App Mesh が API のサービスとして、CodeCommit がソースレジストリとして載っている。QLDB は表3の台帳の行にある。

## 5. ガイドが書いていないこと

- 「このDBが一番いい」という単一の推奨。
- AuroraとRDSの、性能や機能の細かい比較(コスト最適化の表の1行を除く)。
- 具体的なデータ量や性能要件から、DBの種類を決める手順。
- 個別のDBの、設計(テーブル設計、インデックス設計)の進め方。

## 6. 4文で言ってみる

### 1
- **日本語訳**: データの種類で、DBを選ぶ。
- **English**: Choose the database by the type of data.
- **カタカナ**: チューズザデイタベイスバイザタイプオヴデイタ

### 2
- **日本語訳**: リレーショナルデータには、AuroraかRDSを使う。
- **English**: For relational data, use Aurora or RDS.
- **カタカナ**: フォーリレイショナルデイタ / ユーズオーロラオアアールディーエス

### 3
- **日本語訳**: テーブル全体をスキャンせず、インデックスを使う。
- **English**: Don't scan the whole table; use an index.
- **カタカナ**: ドウントスキャンザホウルテイブル / ユーザンインデックス

### 4
- **日本語訳**: DBは、EC2ではなく、マネージドサービスで動かす。
- **English**: Run the database as a managed service, not on EC2.
- **カタカナ**: ランザデイタベイスアザマニジドサーヴィス / ナットオンイーシーツー
