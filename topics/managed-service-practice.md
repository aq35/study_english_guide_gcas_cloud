# 補章: マネージドサービス活用実践ガイドを読む

出典: [GCASガイド「マネージドサービス活用実践ガイド」](https://guide.gcas.cloud.go.jp/modernization-guide)(1〜9章と、別紙のセルフチェックリスト)
英訳は筆者の訳。カタカナの `/` は息継ぎ(ルールは [linking-rules.md](../linking-rules.md))。
「ガイド:」はGCASガイドに書かれていること、「推論:」は筆者の推論。

**注意**: このガイドは、CSPに依らない共通の内容。AWS特有の記述は少ない(下の「AWSでは」を参照)。

## 1. 何のガイドか

- ガイド: 目的は、「作って運用し続ける」構造から、「**作らずに使う**」構造へ転換すること。
- ガイド: オンプレミスのやり方を、そのままクラウドに持ち込むと、コストも運用負荷もオンプレミスと大差ない、または高くなる。たとえば、クラウド上に監視サーバを作ると、OSパッチ、バージョンアップ、ライセンス更新、障害対応を担い続ける。常時稼働が前提なので、従量課金の恩恵も得にくい。
- ガイド: 4つの効果は、コスト最適化、運用負荷軽減、柔軟性向上、セキュリティ向上。
- ガイド: 対象は、アプリや運用方式の改修を最小限にする移行(R1: Replatform)。

### 優先度(ガイドの表2-1)

| 章 | 取り組み | 優先度 | アプリへの影響 |
|---|---|---|---|
| 3 | 監視 | 必須 | 小 |
| 4 | ログ管理 | 必須 | 小 |
| 5 | バックアップ | 必須 | 小 |
| 6 | セキュリティ | 必須(システムの要件に応じて選ぶ) | 小 |
| 7 | データベース | 必須(移行元がマネージド非対応なら、仮想マシン構成もやむを得ない) | 中 |
| 8 | 共有ストレージ | A(オブジェクトストレージ)は推奨、B(マネージドファイルサービス)は必須 | 大 / 小 |
| 9 | サイズの拡張・縮小 | サイズは必須、台数(オートスケール)は推奨 | 小 / 大 |

- ガイド: 「必須」はR1のタイミングで対応する。「推奨」はR1が望ましく、遅くともR2(Rebuild)のタイミングで対応する。

### 進め方と、4つの分類

1. 既存方式の棚卸し → 2. 各章の移行方針表に当てはめる → 3. クラウド設計

| 分類 | 意味(ガイド) |
|---|---|
| 設定のみで対応可能 | クラウドサービスの設定変更だけで実現できる |
| 追加作業あり | エージェントの導入、スクリプト開発などが必要 |
| 設計変更が必要 | クラウドの特性に合わせて、設計を見直す |
| 廃止検討 | クラウドでは不要になる |

## 2. 領域ごとの要点

### 3. 監視

- ガイド: 監視の本来の目的は、CPUやメモリの状態ではなく、**利用者が使うときのレスポンス時間やエラー率(サービス品質)**を見ること。R1では難しいことが多いので、将来のサービス監視を見据えた設計にする。

| オンプレの方式 | 分類 | 要点 |
|---|---|---|
| 死活監視(Ping/ICMP) | 設計変更 | IPが動的に変わるので廃止。コンポーネントごとのヘルスチェックか、外形監視に移す |
| リソース閾値アラート | 廃止検討 | オートスケールがあれば、アラートは不要。なければ、閾値アラームで続ける |
| キャパシティのトレンド監視 | 廃止検討 | 拡張・縮小が柔軟なので重要性が低い。コスト監視に置き換える |
| ネットワーク機器監視(SNMP)、仮想化基盤監視、ハードウェア監視 | 廃止検討 | CSPの責任範囲 |
| ログ監視、サービス監視(URL監視) | 設定のみ | ログのメトリクスフィルタ、外形監視サービス |
| ジョブ監視 | 設計変更 | ワークフローサービスやイベント連携サービスに移す |

新しく必要になる監視: CSPの障害、サービス固有のメトリクス、コスト、セキュリティ関連、サービス品質(まずロードバランサのメトリクス、次にAPM)。

### 4. ログ管理

- ガイド: ログの分析・可視化・長期保管もマネージドで使える。オンプレミスでは難しかったログの分析・可視化を進めて、ログ管理を高度化するのが重要。
- ガイド: コンテナやサーバレスは永続ストレージがないので、ログの外部出力が必須。標準出力(stdout/stderr)に出すと、自動収集される。
- ガイド: 保管は2段階。短期(分析・監視)はログ管理サービス、長期(監査)はオブジェクトストレージ。ログ管理ソフトウェアは、標準機能で足りるなら、継続利用の必要性を見直す(廃止検討)。
- ガイド: クラウドの管理操作ログは、ガバメントクラウドでは必須適用テンプレートで自動設定されるので、個別の設計は不要。

### 5. バックアップ

- ガイド: クラウドのストレージが高耐久なのは、ハードウェア障害への対策。**誤操作・誤削除・ランサムウェアには対応しない**ので、重要データは複数世代や遠隔地レプリケーションを組み合わせる。
- ガイド: 仮想マシンのスナップショット、DBの自動バックアップ、遠隔地(リージョン間コピー)は、設定で実現できる。テープなどの媒体管理は廃止。
- ガイド: **リストア手順の整備と、RPO・RTOを満たす検証**を、事前にやる。バックアップの目的はリストアにある。
- ガイド: CSPの責任範囲のものは、バックアップ不要。バックアップするのは、アプリのデータや設定ファイルなど、利用システムの責任範囲のもの。

### 6. セキュリティ

- ガイド: クラウドは構成が複雑になりやすく、**設定不備によるリスクが高まりやすい**。予防的統制(権限管理、ファイアウォールなど)だけでなく、発見的統制(CSPM、操作ログの監視)と、訂正的統制(設定の自動修復)を組み合わせる。

| 対策 | 分類 | 要点 |
|---|---|---|
| ファイアウォール、WAF、暗号化・鍵管理、CSPM | 設定のみ | 専用機器は不要。WAFはマネージドルールを活用 |
| IDS/IPS、ウイルス対策 | 追加作業 | IDSは脅威検知サービス、IPSはネットワークファイアウォールのルール設定 |
| 脆弱性管理(パッチ) | 設計変更 | パッチ管理サービスで自動化。マネージドでは、パッチのタイミングを選べない場合がある |
| ネットワーク分離(DMZ) | 設計変更 | R1では従来の分離をVPC上で再現。R2でゼロトラストを見据える |

- ガイド: 外部のCSPMサービスは、CSP標準で対応できない要件(マルチクラウドの一元管理など)があるときだけ。過剰な導入になりやすい。

### 7. データベース

- ガイド: HA構成、自動バックアップ、リードレプリカ、リージョン間レプリケーションは、設定だけでできる。
- ガイド: **データベースサーバのOS上で動かしていたバッチや運用スクリプトは、別の環境に移す**(バッチサーバや、サーバレス実行環境)。
- ガイド: **最上位特権(sysdba、SUPER など)の操作は使えない**。パラメータ設定の機能などに見直す。
- ガイド: 移行前後の**動作検証(ノンデグレーションテスト)**が必要。
- ガイド: バージョンアップはCSPが管理するので、タイミングを選べない場合がある。サポート終了前に、バージョンアップ計画を立てる。
- ガイド: R1では、NoSQLへの移行は難しい(アプリ改修が要る)。R2で検討する。

バッチをDBの外に出すと、ネットワークのレイテンシで処理が長くなりやすい。早めに性能検証をして、次の対策を使う。

| 対策 | 内容 |
|---|---|
| SQL発行回数の削減 | ループで1件ずつ発行せず、一括のUPDATE/INSERTにする。ネットワークの往復がN回から1回に減る |
| ストアドプロシージャ | DB内部で完結させる。ただし、DBエンジンを変えるなら書き直しが必要 |
| バッチの抜本的な見直し | イベント駆動化、DB内での完結、並列化 |
| 同一の耐障害性ゾーンに置く | レイテンシは下がるが、ゾーン単位の冗長化が難しくなる。**最終手段** |

### 8. 共有ストレージ

| アプローチ | 内容 | 向いている場面 |
|---|---|---|
| A: オブジェクトストレージ | APIで使う。容量上限なし、従量課金、バージョニング、ライフサイクル管理 | クラウドの活用には望ましいが、アプリ改修が必要 |
| B: マネージドファイルサービス | NFS/SMBのまま使える | アプリ改修を最小限にできる。R1では実用的 |

アプローチAで、事前に確認すること(ガイド):
- **ファイルロックがない**: ロック前提の処理は、アプリ側で排他制御を実装する。
- **部分更新ができない**: 追記などは、ファイル全体の上書きにする。
- **小さいファイルの大量処理は遅い**: 早めに性能検証をする。ファイルの集約やバッチの見直し。
- **最終的整合性**: 作成や削除の直後に、ファイル一覧へ反映されるまで時間差が出る場合がある。
- **意図しない公開**: 設定変更で公開状態になるリスクがある。最小権限と、パブリックアクセス防止機能の有効化。

### 9. サイズの拡張・縮小

- ガイド: クラウド移行でコストが想定より高くなる原因の多くは、**オンプレミス時代のサイジングをそのまま持ち込んだ過剰構成**。サイジングの継続的な見直しは、コスト最適化で最も即効性が高い取り組みの1つ。
- ガイド: 最大負荷を見越した初期サイジングは、廃止。必要最低限のサイズから始めて、運用の中で見直す。長期的なキャパシティ計画も、重要性が下がる。
- ガイド: オートスケールの導入には、アプリ側の対応が必要な場合がある。
  - セッション情報は、サーバの外(マネージドなDBなど)に持つ。スティッキーセッションが不要になる。セッション情報は、認証状態のような最低限に絞る。
  - ファイルやログは、サーバの外(オブジェクトストレージなど)に保存する。
  - スケールインの条件も設定する。台数の**上限**も設定して、DoS攻撃などによる意図しない過剰なスケールアウトを防ぐ。コスト監視も入れる。
  - パッチは、個々の仮想マシンではなく、マスターイメージの更新で行う。
- ガイド: 常時稼働が必要なサーバには、リザーブドインスタンスや節約プランなどの長期継続割引を検討する。

## 3. 「やめとけ」(廃止検討)のまとめ

| やめる | 代わりに |
|---|---|
| Ping/ICMPによる死活監視 | コンポーネントごとのヘルスチェック、外形監視 |
| オートスケールがあるのに、リソース閾値アラートを残す | アラートを廃止 |
| キャパシティのトレンド監視、長期キャパシティ計画 | コスト監視、定期的なサイズ見直し |
| クラウド側のSNMP監視、仮想化基盤監視、ハードウェア監視 | CSPの責任範囲なので不要 |
| ログ管理ソフトウェアの惰性での継続 | クラウドのログ管理サービス |
| バックアップ媒体(テープ)の管理 | クラウドのバックアップサービス |
| 最大負荷を見越した初期サイジング | 必要最低限から始めて見直す |
| CSP標準で足りるのに、外部CSPMを入れる | CSP標準のCSPM機能 |
| ストレージの高耐久性だけに頼る(バックアップなし) | 複数世代・遠隔地を組み合わせたバックアップ |
| DBサーバのOS上のバッチ・運用スクリプトを、そのまま使う | バッチサーバやサーバレス実行環境に移す |

## 4. AWSでは

このガイドは、CSPに依らない共通の内容で、「クラウドの監視サービス」のように書かれる。AWS特有の記述は、次のとおり。

| 場所 | ガイドの記述 |
|---|---|
| 各章の「参考資料」 | AWSのリファレンスアーキテクチャへの案内: 2.15 オブザーバビリティ、2.16 ログ管理、2.11 セキュリティ、2.21 コスト管理(AWS) |
| 7章 | 「Replatformシステム移行ノウハウ(RDBのマネージドサービス化)(AWS編)」への案内 |
| 表9-3(セッション管理サービス) | AWSは、インメモリ: Amazon ElastiCache、キーバリュー: Amazon DynamoDB、リレーショナル: Amazon RDS |
| 注釈 | 耐障害性ゾーンは、AWSでは Availability Zone |

参考(AWS技術ガイドの表より): 各領域のAWSサービスの例。

| 領域 | AWSサービス(AWS技術ガイドの表) |
|---|---|

| バックアップ | 各サービスのバックアップ機能、AWS Backup |
| セキュリティ | AWS WAF、Network Firewall、GuardDuty、Security Hub、KMS |

推論: この対応は、AWS技術ガイドの別の表の分類による。このガイドの各章が、これらのサービスを名指しているわけではない。

## 5. セルフチェックリスト(別紙1-2)から

ガイドには、事業者向け(設計・構築・運用で確認)と、職員向け(事業者への確認、提案の評価、調達仕様書の作成)のチェックリストがある。全部を一度に達成する必要はなく、必須(◯)から確認する。例:

- 監視サーバを個別に構築せず、クラウドの監視サービスを使っているか。
- バックアップのリストア手順を検討して、RPO・RTOを満たすことを確認しているか。
- DBは、マネージドサービスを使う方針か。使わない場合、事業者から理由の説明を受けているか。
- 導入時に過剰なインスタンスサイズ・台数を選んでいないか。
- オートスケールを入れるなら、台数の上限とコスト監視があるか。

## 6. ガイドが書いていないこと

- AWSの各サービスの、具体的な設定手順や設定値。
- 監視項目の具体的な閾値。
- 推論: 具体の設計は、リファレンスアーキテクチャや、各CSPの公式ドキュメントで補う必要がある。

## 7. 5文で言ってみる

### 1
- **日本語訳**: 監視サーバは作らず、クラウドの監視サービスを使う。
- **English**: Don't build a monitoring server; use the cloud's monitoring service.
- **カタカナ**: ドウントビルダマニタリングサーヴァー / ユーズザクラウズマニタリングサーヴィス

### 2
- **日本語訳**: CPUだけでなく、サービスの品質を監視する。
- **English**: Monitor service quality, not just the CPU.
- **カタカナ**: マニタサーヴィスクウォリティ / ナットジャストザスィーピーユー

### 3
- **日本語訳**: 耐久性の高いストレージは、バックアップではない。
- **English**: Durable storage is not a backup.
- **カタカナ**: デュアラブルストレージ / イズナットアバックアップ

### 4
- **日本語訳**: 小さく始めて、わかってきたらサイズを変える。
- **English**: Start small and resize as you learn.
- **カタカナ**: スタートスモール / アンドリサイズアズユーラーン

### 5
- **日本語訳**: セッションは、サーバの外に持つ。
- **English**: Keep the session outside the server.
- **カタカナ**: キープザセッションアウトサイドザサーヴァー
