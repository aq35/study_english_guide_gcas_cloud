# 補章: アプリの作り方 — やったほうがいい / やめたほうがいい

出典: [GCASガイド「ガバメントクラウドにおけるモダン化の定義」](https://guide.gcas.cloud.go.jp/general)(モダン化実践ガイド) / AWS技術ガイド
英訳は筆者の訳。カタカナの `/` は息継ぎ(ルールは [linking-rules.md](../linking-rules.md))。
「ガイド:」はGCASガイドに書かれていること、「推論:」は筆者の推論。

## 全体像

- ガイド: ガバメントクラウドの「モダン化」は、最先端の実験的な技術ではなく、「ある程度一般化した新しい技術」を使う方針。安定性が求められるから。
- ガイド: モダン化の定義は5つ(2025年現在)。この定義以外のあり方も、今後検討する。
  1. APIベースのシステム構成
  2. ステートレスなアーキテクチャ
  3. マネージドサービスの活用
  4. 運用のコード化、自動化
  5. サービスレベルの定義、計測
- ガイド: R1(Replatform)は、3を原則求められる。R2(Rebuild)は、1〜5の実現を求められる。ただし、すべてを完全に満たす必要はない(例外は概要解説の第6章)。

## やったほうがいい / やめたほうがいい

### 1. APIベースのシステム構成

| やったほうがいい | やめたほうがいい | ガイドの理由 |
|---|---|---|
| システム間を疎結合にして、API(REST、GraphQL、gRPC など)で連携する | バッチ的な連携(従来の、ファイル転送・ディスク共有・DB共有など。密結合になりやすい) | APIだと、連携するデータが常に最新になる。順次処理なので、エラー処理が容易で、障害の影響も小さくなる |
| API呼び出しは、非同期にする。時間がかかる処理は、受け付けた時点でAPIを一度終了し、あとで結果を取る(ポーリングか完了通知) | 相手の処理の完了を待ち続ける | フロントとバックの非機能要件(性能、信頼性など)を、別々に考えられる |
| API側のエラーを、わかりやすいメッセージにして示し、リトライする(サーキットブレーカー) | エラーを、そのまま利用者に見せる | |
| APIの定義(使い方、オプション、レスポンスの意味)を、利用側に公開する | 定義を公開しない | |
| 既存のAPI定義は、項目の追加に留める | 既存のAPI定義を、変更・削除する | 呼び出し元への影響を最小限にするため |
| データの「名称」「フォーマット」「意味」「目的」「更新頻度」などを、明示する | 定義しないまま渡す | 提供側と利用側が、独立してデータを管理・利用できる |
| フロントエンドとバックエンドを、APIで分ける | | フロントだけで、柔軟に頻繁に更新できて、開発速度が上がる |
| バッチ処理を、イベント駆動にする | 夜間バッチを、そのまま続ける | 夜間バッチは、止まると翌日の業務に響き、オペレーターが監視し続ける必要がある。クラウドは、必要なときに必要なだけリソースを足せるので、夜間にする必要がない |

### 2. ステートレスなアーキテクチャ

| やったほうがいい | やめたほうがいい | ガイドの理由 |
|---|---|---|
| どのサーバで処理しても同じ結果になるようにする。セッション情報などは、サーバの外に保存する | サーバにセッション情報や構成情報を持たせる。負荷分散装置で、振り分け先を固定する | 障害でクライアントの情報が失われない。負荷に応じて、台数を増減しやすい(スケールしやすい) |
| コンテナは、ステートレスでイミュータブルにする(変更は、イメージを作り直す) | コンテナのイメージに、環境固有の情報を入れる | 可搬性が高くなる。CI/CDでのデプロイ自動化や、追加・削除が簡単になる |
| コンテナは、クラウドの機能かマネージドのオーケストレーションツールで運用する | `docker` コマンドで、コンテナを管理・運用する | オーケストレーションツールには、オートスケールとセルフヒーリングがある |
| オートスケールを使う | 台数を、手で増減する | 運用負荷の低減、コストの最適化、可用性の向上が期待できる |

### 3. マネージドサービスの活用

| やったほうがいい | やめたほうがいい | ガイドの理由 |
|---|---|---|
| 監視、ログ管理、バックアップ、セキュリティ、データベースは、マネージドサービスで作る | 監視サーバ、ログ管理サーバ、バックアップサーバを、独自に立てる。仮想マシンにログインして、DBなどを構築する | 構築や運用が容易になる。多くは使った分だけの課金なので、一般に低コスト |
| 共有ストレージは、オブジェクトストレージにして、APIで連携する | NFSファイルサーバを、そのままクラウドサービスに置き換える | そのままだと、一般に高価で密結合になり、耐障害性が低い。ステートレスなら、そもそも共有ストレージが不要 |
| 負荷に応じて、インスタンスやDBのサイズを、拡張・縮小する(自動でできるサービスなら、なおよい) | | コストの最適化と、サイジングの簡素化 |
| セキュリティは、クラウドの機能やOS標準の機能で、合理的なリスク判断のうえ、過剰にならないようにする | 過剰なセキュリティ対策 | クラウドは、外部からの攻撃を自動で防ぐ。利用者が管理するのは、明示的に開けたポートだけ。マネージドなら、パッチも自動で当たる |
| バックアップは、クラウドのバックアップ機能を使う。災害対策には、別リージョンへのコピー | オブジェクトストレージのデータを、障害対応のためにバックアップする | オブジェクトストレージは、自動的に複数ゾーンにコピーされるため |

### 4. 運用のコード化、自動化

| やったほうがいい | やめたほうがいい | ガイドの理由 |
|---|---|---|
| インフラは、IaCで構築・変更する。CI/CDと連携させる | コンソールやコマンドで、手作業で変更する | 手作業はミスが多い。手順書とダブルチェックだけでは、ミスをなくせない |
| 定型作業を、自動化・無人化する | | |
| 本番環境には、ログインしない(Zero Touch Production)。非常時のログインだけを、例外として厳格に管理する | 本番環境に、人が入って手で変える | セキュリティリスクが大きく減る。踏み台サーバとそのログ取得が不要になる。監査の管理ポイントも減る |
| デプロイ戦略を選ぶ(Rolling Update、Blue-Green、Canary など) | | 無停止でリリースできる。新旧を並行稼働させれば、バグの影響を小さくして、ロールバックできる |
| 無停止デプロイは、サービスレベルの範囲で選ぶ | 無停止にこだわる | 無停止のデプロイ戦略は、コスト増になる場合がある。停止を許容する判断も必要 |
| 障害対応を、自動化・リモート化する(死活監視と自動再起動、自動フェイルオーバー、オートスケール、セルフヒーリング) | 繰り返しの手作業(トイル)を残す | エンジニアがより作業に集中できる |
| DBやストレージなどの永続データのサービスは、IaCの管理から外すなどの工夫をする | 永続データのサービスを、注意せずに、他のリソースと同じようにIaCの管理に含める | 永続データは、IaCでの管理に注意が必要(ガイドは「外す等の工夫」と書く) |

### 5. サービスレベルの定義、計測

| やったほうがいい | やめたほうがいい | ガイドの理由 |
|---|---|---|
| 提供する価値を、KPI(稼働率、レスポンス、エラー率、登録ユーザー数など)として定義する | | 価値を定量的に表せる |
| サービスレベルを、計測できる値で決める(例: 稼働率99.5%)。ダッシュボードで可視化する | | |
| 日次・週次で確認して、優先度をつけて改善する | サービスインしたら、そのまま放置する | クラウドは構成を変えやすいので、サービスイン後も継続的に変えるのがベストプラクティス |
| 可視化は、改善につながるものに絞る。ダッシュボードで、常に最新の情報を見せる | 監視項目を増やしすぎる。定型の月次報告書だけで説明する | |

## AWSで言うと

ガイドの表(AWSサービスの活用)に出てくる、各分野のサービス。

| 分野 | AWSサービス(ガイド) |
|---|---|
| API | Amazon API Gateway |
| コンピュート(サーバレス / コンテナ) | AWS Lambda / Amazon ECS、EKS、App Runner |
| イベント駆動 | Amazon SNS、SQS、EventBridge(バッチの置き換えの実装例) |
| 共有ストレージ代わり | Amazon S3 |
| 監視・ログ | CloudWatch(Metrics、Logs)、X-Ray、CloudTrail |
| バックアップ | 各サービスのバックアップ機能、AWS Backup |
| セキュリティ | AWS WAF、Shield、Network Firewall、Secrets Manager、KMS、Security Hub、GuardDuty |
| IaC・デプロイ | AWS CloudFormation、CodeBuild、CodeDeploy、CodePipeline、Amazon ECR(コンテナレジストリ) |
| バッチ処理 | AWS Step Functions、Amazon MWAA、SWF |
| 踏み台 | Systems Manager Session Manager |

推論: 「本番にログインしない」と「Session Manager(踏み台)」は、いっけん矛盾する。ガイドは、非常時のログインだけを例外として管理すると書いているので、Session Manager は、その例外のためのログイン手段だと読める。ガイドはこの対応を明示していない。

## ガイドが書いていないこと

- プログラミング言語やフレームワークの、選び方(モダン化の定義には出てこない)。
- テストの進め方、コーディング規約。
- 個々のAWSサービスの、設計の細かい指針(この章は、考え方の指針)。
- 推論: CI/CDの詳しい進め方は、別の資料(デリバリーパイプラインの資料)にある。この章では読んでいない。

## 5文で言ってみる

### 1
- **日本語訳**: サーバに、状態を持たせない。
- **English**: Don't keep state on the server.
- **カタカナ**: ドウントキープステイトオンザサーヴァー

### 2
- **日本語訳**: APIは非同期で呼び、答えを待ち続けない。
- **English**: Call APIs asynchronously; don't wait for the answer.
- **カタカナ**: コールエイピーアイズエイスィンクロナスリ / ドウントウェイトフォジアンサー

### 3
- **日本語訳**: マネージドサービスを使い、自前の監視サーバは作らない。
- **English**: Use managed services; don't build your own monitoring server.
- **カタカナ**: ユーズマニジドサーヴィスィズ / ドウントビルドヨアオウンマニタリングサーヴァー

### 4
- **日本語訳**: インフラは、手作業ではなく、コードで作る。
- **English**: Build infrastructure with code, not by hand.
- **カタカナ**: ビルドインフラストラクチャウィズコウド / ナットバイハンド

### 5
- **日本語訳**: 本番環境には、ログインしない。
- **English**: Don't log in to production.
- **カタカナ**: ドウントログインチュプロダクション
