## 1. 移行の全体像: 評価 → 計画 → 実行

- ガイド: 移行は、**現在の状態を把握し、移行計画を検討し、実行に移す**プロセス。AWSの活用も含めて検討するタスクを、本ガイドが示す。

| 段階 | やること | ガイドが挙げるAWSサービス |
|---|---|---|
| 全体管理 | 移行全体の計画・実行・進捗を、1つのダッシュボードで追う | AWS Migration Hub(無料) |
| インフラ資産把握 | 既存サーバーの設定・使用状況・依存関係を集める | AWS Application Discovery Service |
| 経済性評価 | 現状を分析して、AWSへ移したときのコストを予測し、ビジネスケースを作る | AWS Migration Evaluator |
| アーキテクチャ検討 | Replatform / Rebuild / Repurchase のどれにするか | (次の節) |
| 運用管理・セキュリティの検討 | マネージドサービスで、運用工数とライセンスを減らす | (表4) |
| 移行方式の検討 | 要件を整理して、移行方式を選ぶ | (第3節) |
| 実行 | データ・DB・アプリ・ネットワークを移す | DataSync、Snow Family、Transfer Family、DMS、Mainframe Modernization |

ガイドが、わざわざ書いている注意:
- **Rehost(リフト&シフト)では、ガバメントクラウドを利用できない**。Replatform / Rebuild / Repurchase の3パターンで検討する。
- **BYOL(既存ライセンスのクラウドへの持ち込み)は、原則禁止**。
- Application Discovery Service には、**1日10GBの上限**がある(エージェントレス型は、上限に達すると翌日まで処理できない。エージェント型は、AWS認定パートナーのみ利用可)。
- Migration Evaluator は、ストレージアプライアンス、メインフレーム、ネットワーク機器のモニタリングやレポート向けには、設計されていない。
- 移行テストは、**AWSの責任範囲は実施しない**など、移行パターンに合わせて必要なテストだけを実施し、移行コストを最適化する。
- ガバメントクラウドでは、AWS Shield は **Advanced ティア**が使える。

推論: 「移行テストでAWS側の責任範囲を見直さない」は、責任共有モデル([原則4](../principles/04-shared-responsibility/README.md))の移行版だと読める。

## 2. パターンごとに使うAWSサービス

### Replatform(アプリ一部変更移行)

- ガイド: 基本形は、運用・セキュリティ・RDB・ストレージを**マネージドサービス化**し、共有ストレージには**オブジェクトストレージ**を使う。例外は、既存のDBMSがマネージドに対応していない場合に、RDBをサーバーインスタンスへインストールする構成。

| カテゴリ | 機能 | 主なAWSサービス |
|---|---|---|
| データベース | RDB | Amazon Aurora / Amazon RDS |
| ストレージ | オブジェクトストレージ | Amazon S3 |
| ネットワーク | ネットワーク / CDN / DNS / NTP / 負荷分散 | VPC / CloudFront / Route 53 / Time Sync Service / Elastic Load Balancing |

- ガイド: 有償ライセンスの Oracle Database と SQL Server は、RDS for Oracle / RDS for SQL Server で動くが、**エディションによってはAWS上でサポートされない**。使えるエディションは、AWSのFAQで確認する。

### Rebuild(アプリ再構築移行)

- ガイド: サーバーレスとコンテナが前提。基本形1はマイクロサービス、基本形2はフロントとバックエンドAPIの分離・イベントドリブン・最適なデータ基盤への変更。例外は、長期塩漬けシステム向けの、アプリサーバーのコンテナ化移行。
- ガイド: APIは API Gateway、サーバーレスは Lambda、コンテナは ECS / EKS が主なサービス。
- ガイド: DBは、データの種類で選ぶ(リレーショナル=Aurora/RDS、キーバリュー=DynamoDB、ドキュメント=DocumentDB、インメモリ=ElastiCache/MemoryDB、グラフ=Neptune、時系列=Timestream、ワイドカラム=Keyspaces)。詳しくは [DBの補章](aws-db-and-donts.md) を見る。

### 運用管理・セキュリティ・CI/CDの主なサービス(ガイドの表4から、太字の主要サービス)

| カテゴリ | 機能 | 主なAWSサービス |
|---|---|---|
| 運用 | バッチ / バックアップ / ログ / 変更管理 | Step Functions / AWS Backup / CloudTrail・CloudWatch Logs / AWS Config |
| 運用 | インベントリ・自動化 / 踏み台 | Systems Manager / Systems Manager Session Manager |
| 運用 | コスト管理 | Cost Explorer / Budgets / Trusted Advisor |
| 運用 | モニタリング・検知 | CloudWatch Metrics・Alarms / X-Ray / EventBridge |
| CI/CD | レジストリ・ビルド・デプロイ・パイプライン | ECR / CodeBuild / CodeDeploy・CloudFormation / CodePipeline |
| セキュリティ | 全体管理 / 脅威検知 / 評価 | Security Hub / GuardDuty / Inspector・Trusted Advisor |
| セキュリティ | 認証 / 暗号化キー / 証明書 | Cognito・Secrets Manager・Directory Service / KMS / ACM |
| セキュリティ | WAF / DDoS / ファイアウォール | AWS WAF / AWS Shield / Network Firewall |

## 3. 移行方式の選び方

### 3.1 移行要件を整理する

- ガイド: ビジネス、作業、技術の3分類で要件を出し、**優先順位をつけて**から、要件を満たす方式を選ぶ。

| 分類 | 要件の例 |
|---|---|
| ビジネス | 業務停止可能時間 / 停止可能回数 / 移行コスト / 既存業務への影響 / 法令遵守 |
| 作業 | 作業の複雑性 / 所要時間 / 作業連携・分担の複雑性 |
| 技術 | 移行実施単位 / 切り戻しの容易さ / 回線速度と移行性能 / 現行構成の変更の有無 |

### 3.2 3つの軸で選ぶ

ガイドは、**システム移行方式 → データ移行方式 → 業務切り替え方式**の順に決める。政府機関では「システム一括移行、データ一括同期、ユーザー/ロケーション/業務順次切替え」が多いと想定している。

| 軸 | 方式 | ガイドの説明 | 向く場合 |
|---|---|---|---|
| システム移行 | 並行稼働 | 新環境を作って旧環境と並行稼働。安定したら旧環境を切り離す | 可用性要求が高い大規模システム。モダン化したアーキテクチャの運用に不安があり、いつでも旧環境へ戻したい |
| システム移行 | サブシステム順次 | サブシステム・機能ごとに順次移行 | 一括だと開発スケジュールがタイトな大規模システム。新しい法律に係る機能を新環境で作るなど |
| システム移行 | 一括 | 1回の作業で全部移す | 移行コストを抑えたい、移行期間が短い |
| データ移行 | リアルタイム同期 | 停止時間なし。新旧をアプリレベルで同期して稼働し、旧環境を止める | 停止できない |
| データ移行 | 事前同期 | 停止時間は中。切替え前に同期し、旧環境の停止後に差分を同期 | 短い停止なら許容できる |
| データ移行 | 一括同期 | 停止時間は大。旧環境を止めてバックアップを取り、新環境でリストア | 長い停止を許容できる |
| 業務切り替え | 順次移行 | 特定の部門・地域を先行する | 部門・地域ごとに影響度が違う。影響の少ない所から |
| 業務切り替え | 一括移行 | 全部門・全地域を一括 | コストを抑えたい、期間が短い |

システム移行方式の比較(ガイドの表7、要約):

| 方式 | コスト | リスク | 作業負荷 | 期間 |
|---|---|---|---|---|
| 並行稼働 | 大(旧環境の維持と新旧のネットワーク接続) | 小(旧環境へ切り戻せる) | 大 | 長(新環境の正常性判断期間) |
| サブシステム順次 | 大(新旧のネットワーク接続) | 小(トラブル範囲は移行対象のみ) | 大 | 長(複数回の移行) |
| 一括 | 小(移行作業のみ) | 大(切り戻せない) | 小 | 短 |

ガイドが書いている注意:
- データ移行で業務が止まる時間は、**前処理 + データ移行 + 後処理**の合計。**移行失敗時の切り戻しも含めて**見積もる。
- AWSでは、利用者がデータセンターに入館できないので、オンプレより**物理移行の期間が長くなる**。
- 旧環境のネットワークが転送速度のボトルネックなら、**GSSにデータを持ち込み**、速いGSSネットワーク経由で新環境へ送る方法も検討する。
- 旧環境のネットワークはブラックボックス化していたり、GSSの仕様があったりするので、**早めにプロトコルの疎通確認と転送速度の確認**をする。
- ガバメントクラウドの移行とGSSの移行を並行して検討しているなら、**どちらを先にするか、同時にできるか**を検討する。

### 3.3 データの運び方

| 方法 | サービス | ガイドの説明 |
|---|---|---|
| オンライン(インターネット / Direct Connect) | AWS DataSync | NFS・SMB・S3・EFS・FSx間などを簡単・自動・高速に転送。暗号化と整合性検証あり |
| オンライン + ローカルネットワーク | AWS Transfer Family | SFTP / FTPS / FTP / AS2 でS3・EFSへ。**プロトコルの性質上、大量データには向かない** |
| オフライン | AWS Snow Family(日本リージョンで使えるのは Snowcone と Snowball) | 物理デバイスを送って運ぶ。Snowcone は8TB(SSD版は14TB)。Snowball の例: 250TBのS3アップロードが1〜2.5日、運搬込みで約10日 |
| DB | AWS DMS + SCT | スキーマをSCTで変換し、マネージドDBを用意して、DMSで移す。1回限りの移行後、継続的な変更のレプリケートもできる |
| アプリ(メインフレーム) | AWS Mainframe Modernization | 互換性を残したリプラットフォームと、自動リファクタリングの2パターン |

- ガイド: アプリの移行は、マイクロサービス・API・コンテナなどのモダン化が前提。ただし**段階的にモダン化する**などの理由でリビルドせずに移すなら、アプリ移行サービスで工数と期間を減らす。

## 4. Replatform ノウハウ(1): クラウドサービス活用 — オートスケールとマルチAZ

- ガイド: 推奨は、**オートスケール**(台数を負荷に応じて増減)と、**コンテナ化**(依存関係ごとイメージ化。同じイメージをテスト環境で検証してから本番へ)と、**マルチAZ**(可用性の向上)。コンテナは、フルマネージドのサービスをデプロイ先にすれば、ホストの仮想サーバーの管理も不要になる。
- ガイド: 前提とするサービスは、仮想マシンが Amazon EC2、コンテナが Amazon ECS(コントロールプレーン)+ AWS Fargate(データプレーン)。

### オートスケール対応: 「サーバーの中に何も持たない」

| テーマ | ガイドの方針 | 理由(ガイドの説明) |
|---|---|---|
| セッション管理 | セッション情報は**サーバーの外**(ElastiCache / DynamoDB / RDS / MemoryDB などのマネージドDB)に保持する。複数の処理にまたがるトランザクションの状態は、セッション情報にしない(サーバー側はステートレス) | 台数が増減しても、どのサーバーでも応答できる。**スティッキーセッションが不要**になる |
| ファイル | 一時ファイルやアップロードファイルは**サーバーの外**に置く。保存先は **S3**。ミドルウェアの制約など、やむを得ない場合を除き、ファイルストレージは避ける。必要でも EFS や FSx for Windows などのマネージドにする | 台数が増減しても、すべてのサーバーがファイルを使える |
| ログ(仮想マシン) | 永続化が必要なログは **CloudWatch Logs** にアップロードする(CloudWatchエージェント)。アプリの監視に使わないログは、S3も選べる(検索機能はないが、長期保管は安い) | スケールインでサーバーが消えても、ログが残る |
| ログ(コンテナ) | アプリは**標準出力**に出力する。ログドライバーが CloudWatch Logs 等へ運ぶ(awslogs=設定が簡単、Firelens=S3など多様な転送先と高度な処理) | 保管先を変えるときは、ログドライバーの設定変更だけでよい |
| パラメータ管理 | 設定値と認証情報は、サーバーの**外**(Parameter Store、Secrets Manager)に置く | 環境ごとにビルドし直さなくてよい。設定を変えても再ビルド不要 |
| シャットダウン(コンテナ) | 終了シグナル(SIGTERM)を受けて、安全に終了する。タイムアウト後に SIGKILL で強制終了される | グレースフルに終了し、ファイルを退避する |

- ガイド: 性能検証。オートスケールを入れたら、**最大の同時リクエスト数**とアクセスパターンで負荷試験をし、レイテンシ、スループット、ステータスコード(高負荷時も成功しているか)を確認する。スケーリングの基準値と最小・最大キャパシティは、**継続的に見直す**。一時的なアクセス増が見込まれるなら、あらかじめ最小キャパシティを上げる**スケジュールスケーリング**も有効。
- ガイド: EC2から負荷試験をするときは、「Amazon EC2 Testing Policy」で「ネットワーク負荷テスト」に該当するかを確認する。

### マルチAZ対応

- ガイド: ELB(ALB=HTTP/HTTPS・L7、NLB=TCP/TLS/UDP・L4)で負荷を分散する。クライアントは**ELBのホスト名**で接続する。CLB(旧世代)は、ほとんどの場合 ALB か NLB で足りる。
- ガイド: AZ間は高帯域・低レイテンシだが、**AZをまたぐ通信が増えると遅延が積み上がる**。対象件数が多いときは、1件ずつDBを更新せず、**一括で更新するようにクエリを見直す**。

### その他

| テーマ | ガイドの方針 |
|---|---|
| 依存関係 | 必要なライブラリを暗黙に頼らず、**明示的に宣言**する(maven/pom.xml、npm/package.json、pip/requirements.txt など。コンテナなら Dockerfile) |
| サービス呼び出し | DBやストレージ、外部APIは、**ネットワーク越しのバックエンドサービス**として扱う。**リトライ**と**タイムアウト**を設ける。AWS SDK は、エクスポネンシャルバックオフ(待ち時間を徐々に長くするリトライ)を実装済み |
| 認証管理 | 独自の認証ではなく、標準仕様(**OIDC**)に従うことが求められる場合がある(職員認証サービス(GIMA)など)。アプリは RP として、認可リクエストの生成、認可コードの受信、アクセス可否の判断を実装し、OPにクライアントを登録する |
| 静的Webサイト | VM上のApache/nginxで配信せず、**S3 + CloudFront** にすると、ストレージ費とアクセス増の考慮が減る |

## 5. Replatform ノウハウ(2): RDBのマネージドサービス化

- ガイド: DBの**マネージドサービス化は、必須で検討し、阻害要因がなければ適用を推奨**する。

### 5.1 サービスを選ぶ

- ガイド: 現行踏襲(同じDBを使う)を大前提にせず、**運用要件、コスト、メンテナンス性**で選ぶ。リレーショナルだけでなく、業務とデータの特性に応じて**非リレーショナル**を選ぶと、性能面のメリットや、RDBの制約にとらわれない利用ができる。選択はフローチャート(データの完全性が必要か → 負荷に法則性があるか → ...。法則性がなければ Aurora Serverless v2 が推奨)に沿う。

### 5.2 製品固有機能は、3つの方針で整理する

| 移行方針 | 意味 | 例(ガイド) |
|---|---|---|
| 同等機能利用 | 移行先にも同じ機能がある | 監査機能 |
| 代替機能利用 | 同等はないが、似た機能で代える | バックアップ(DB製品固有機能 → AWS Backup) |
| 廃止 | 移行先に機能がないので、使うのをやめる | 結果キャッシュ(バッファキャッシュがあるので廃止) |

管理・運用項目の置き換え(ガイドの表2):

| 運用項目 | 従来 | マネージドサービスでの例 |
|---|---|---|
| バックアップ | DBMSのネイティブ機能 | AWS Backup |
| 障害監視・イベント監視 | エージェント型の監視製品 | CloudWatch Logs / EventBridge / RDSのイベント通知 |
| 性能監視 | エージェント型の監視製品 | CloudWatch Metrics |
| アクセス監査 | DBMSの監査機能 | CloudWatch Logs |
| キャパシティ管理 | エージェント型の監視製品 | RDS Performance Insights |
| メンテナンス | 手動パッチ、または適用凍結 | メンテナンスウィンドウによる自動適用 |

### 5.3 可用性

| レベル | 構成 | 守る範囲 |
|---|---|---|
| ① Single-AZ | 1つのAZ内で、部品レベルの冗長化 | ハードウェアの部品障害 |
| ② Multi-AZ | 2つ以上のAZ | データセンター単位の障害 |
| ③ Multi-Region | 2つ以上のリージョン | リージョン単位の障害 |

- ガイド: Multi-AZ は2方式。**Active-Standby**(スタンバイにレプリケート。RDSの全エンジンで可)と、**Multi-AZ DB Cluster**(2つのリードレプリカへレプリケートし、障害時に昇格。RDSではMySQLとPostgreSQLのみ。Auroraも同様)。DynamoDB・Neptune・Keyspaces・Timestream は標準でマルチAZ。ElastiCache・MemoryDB・DocumentDB は、クラスタ構成を選ぶ。
- ガイド: Multi-Region は、東京と大阪を例に、Aurora=Global Database、RDS=クロスリージョンリードレプリカ(**RDS for SQL Server は不可**)、DynamoDB=Global Tables。Global Database には、Aurora MySQL のマルチマスターや Aurora PostgreSQL のクラスターキャッシュが使えないなどの制約がある。**DB以外も合わせてリージョン間でフェイルオーバーする仕組みが必要**。

災害対策のレベル(ガイドの表5):

| レベル | RPO例 | RTO例 | 例 |
|---|---|---|---|
| バックアップリストア | 24時間 | 1か月程度 | AWS Backup、RDS Snapshot、S3 Replication |
| パイロットライト | 数分 | 数時間 | RDSクロスリージョンリードレプリカ |
| ウォームスタンバイ | 数秒 | 数分 | RDSクロスリージョンリードレプリカ |
| ホットスタンバイ | リアルタイム | 数十秒 | Aurora Global Database、DynamoDB Global Tables |

### 5.4 拡張性と運用

- ガイド: スケールは、できるだけ**自動調整やサーバーレス**に。ストレージは自動拡張を有効にし(上限は設定が要る)、読み込みが多いなら**リードレプリカを自動増減**する。負荷に法則性がなく急変するなら Aurora Serverless v2。リードレプリカだけをServerlessにもできる。
- ガイド: 1つのSQLがリソースを占有したり、遅延が続いたりするなら、**リソースを増やす前に機能分割**を考える(OLTPとOLAPのDB分割、読み込みの前に**キャッシュ**、書き込みの前に**キュー**(SQS)で非同期化)。
- ガイド: マネージドDBでは、**インスタンス上のスクリプト実行、DBAタスク、OS領域へのアクセスができない**(一部オプションを除く)。RDS Custom for Oracle ならOSアクセスできるが、**BYOLが必要**なので、コストと必要性を検討する。データ抽出は Glue / EventBridge + Lambda に、ユーザーが起動するオンラインバッチは**アプリ化**する。
- ガイド: パッチの**凍結は基本できなくなる**。メンテナンスウィンドウを決め、ステージング環境で入念に確認して、本番は接続確認にとどめるなど、テストを効率化する。DynamoDBは自動更新で考慮点は特にない。

### 5.5 データ移行

- ガイド: 方式は、**停止許容時間**と**データ量**で選ぶ。

| 停止許容時間 | ツール例 |
|---|---|
| 数分 | DBエンジンのレプリケーション、ログシッピング |
| 数時間 | バイナリダンプ、ログシッピング |
| 数日 | バイナリダンプ、CSVダンプ |

| データ量 | 転送方式 |
|---|---|
| 〜数100GB | Transfer Family、DMS、DataSync、Snowball |
| 〜10TB | Transfer Family、DMS(CDC)、DataSync、Snowball |
| それ以上 | DMS(CDC)、DataSync、Snowball |

- ガイド: 道具の役割分担は、**DMS**=データを移す(8並列が基本。帯域が足りなければ並列度を下げ、その分時間がかかる。ソース側のネットワークにDMSエージェント用のLinuxサーバーが要る)、**SCT**=スキーマ(DDL)を変換する、**Glue**=単純な型変換でなく、計算した結果を登録したいときのETL。
- ガイド: どのツールも、移行元と移行先を**ネットワークでつなぐ**必要がある。経路が確保できないなら、DBエンジンのダンプやCSV出力を含めて広く検討する。
- ガイド: Snowball は、破損に備えて**予備機も一緒に注文**する(台数の上限が初期値で1台なので、上限緩和申請が要る)。
- ガイド: 第1期政府共通プラットフォーム(第1期PF)からの移行は、DBセグメントから外部へ通信できない場合がある。DMZに移行用サーバーを置く案もあるが、**調整の準備期間**が要る。Snowballでは第1期PFのデータセンターへの**立入り作業**が要り、立入り可能な時間に制約があるので、**早めにスケジュールを調整**する。

## 6. Replatform ノウハウ(3): オブジェクトストレージ(S3)

| テーマ | ガイドの方針 | 理由 |
|---|---|---|
| 方針 | コスト効率を考え、**可能な限りS3に保管**する。アプリへの影響が大きいなら、可能な範囲で | — |
| アクセス方法 | **最新のAWS SDK**を使う | パフォーマンス最適化のガイドラインが組み込まれ、更新される。HTTP 503の自動リトライもある。SDKを使わないなら REST API だが、署名の生成とリトライはアプリで実装する |
| オブジェクトキー | 中間ファイルをS3に置くなら、**オブジェクトキー名をDBに保管**する(セッション管理で挙げたDBから選ぶ) | 後続の処理で、そのファイルをダウンロードできる |
| ライフサイクル | 中間ファイルなど長期保管が不要なものは、**S3ライフサイクルで自動削除**する | アプリのエラーでファイルが残っても消える。ルールはバケット全体、タグ、prefix で絞れる |

## 7. Replatform ノウハウ(4): バッチ処理の改革と、監視の移行

### 7.1 バッチ: 「スケジューラー」と「実行コンピュート」を分けて選ぶ

| 役割 | 選び方(ガイド) |
|---|---|
| スケジューラー | **EventBridge Scheduler** が推奨。既存のIaCテンプレートを使い回したいなど、使えない理由があるときだけ EventBridge Rule |
| オーケストレーター | ETLなら **Glue**。ETL以外で繰り返し・並列・エラー処理などが要るなら **Step Functions**(失敗したジョブの途中実行ができない点を念頭に設計)。オープンソース性、他クラウドへの可搬性、他クラウドのSDK呼び出しが多いなら MWAA(Airflow)。外部シグナルでの介入や、結果を親に返す子プロセスが要るなら SWF |
| 実行コンピュート | Lambdaで足りるなら **Lambda**(**15分の上限**。15分以内のサブタスクに分けられれば可)。15分を超える、またはLambdaで非対応の言語・ツールなら **ECS on Fargate**。GPUなど特殊なインスタンスが要るなら EC2 または ECS on EC2。コンテナ化が困難(特殊なOSなど)なら EC2 |

- ガイド: ECS on EC2 は運用保守の負荷が大きいので、Lambda や Fargate のようなサーバーレスで実現が困難な場合に限って検討する。EC2は、特殊なデバイスや特殊なOSで、コンテナイメージが入手できない場合に限る。
- ガイド: バッチは、ストレージ容量・物理サーバー・ミドルウェア・外部連携の制約が外れる観点で**見直す**。単純移行はクラウドリソースの浪費になる。ファイル配置などのイベントで起動する(イベントドリブン化)、API で外部データを常時取得する、オンデマンドのリソースでオンライン処理にする(バッチの廃止)、といった方向がある。
- ガイド: バックアップも、ソフトウェアやジョブでやる方式を見直す。法令・監査にはアーカイブ(S3 Glacier)、遠隔地保管(クロスリージョンレプリケーション)、削除防止(オブジェクトロック)。操作ミスにはバージョニングとポイントインタイムリカバリ。

### 7.2 監視の移行

- ガイド: 監視は、**必須で検討し、阻害要因がなければ適用を推奨**する。
- ガイド: Observability(観測可能性)の要件は5つ。①問題発生時のアラーム、②原因調査に必要な情報、③長期の計画のための傾向、④更新の前後・版の比較、⑤重要な情報の可視化。集めるデータは、**メトリクス**(ある時刻の数値)・**ログ**(イベントの記録)・**トレース**(サービスをまたいだ連鎖の記録)の3種類。
- ガイド: 最低限見る4つの項目は、**レイテンシー、トラフィック、エラー、飽和度**。レイテンシーは、成功時とエラー時を**別々に**集計する(瞬時に返るエラーが、成功時の平均を良く見せてしまうため)。エラーは、5XXだけでなく、HTTP 200でも内容が誤っている場合や、許容を超える遅延も含む。

| 役割 | サービス |
|---|---|
| 計測 | CloudWatch Logs / Metrics / Synthetics(外形監視)、Budgets、Trusted Advisor、CloudTrail、GuardDuty、Inspector、Config Rules、Health、X-Ray、OpenTelemetry |
| 連携 | CloudWatch Alarm、EventBridge、Security Hub |
| 通知 | SNS、AWS Chatbot(Slack連携) |
| 保管 | S3、CloudWatch Logs / Metrics、Kinesis Data Firehose |
| 可視化 | CloudWatch Dashboard、QuickSight、X-Rayコンソール |

- ガイド: 通知は、緊急度で3つに分ける。

| 種類 | 意味 | 例(ガイド) |
|---|---|---|
| ページ | 即時対応が必要 | 5XXエラーの多発。応答時間が正常値を大幅に超える |
| チケット | 数日以内に対応 | サーバーCPU使用率100%。週次バックアップの失敗 |
| ロギング | 対応は不要だが記録する | ヘルスチェックに失敗したインスタンスが自動で置換された。少量の4XXエラー |

ガイドの理由: **ページは厳密に限定する**。不要なページが多発すると、運用者に無駄な負担をかけ、本当に緊急なページへの緊張感がなくなる。**一度ページされた事象は、再発しないよう根本原因の解決か自動化を検討する**。

## 8. 「やったほうがいい / やめとけ」

左の列はガイドの方針。右の列は、ガイドが直接「やめろ」と書いたもの(Rehost、BYOL)を除き、**左の裏返しとして筆者が書いた推論**(ガイドの文面ではない)。

| やったほうがいい(ガイド) | やめとけ(推論。Rehost・BYOLのみガイド) |
|---|---|
| 移行要件に優先順位をつけてから、方式を選ぶ | 移行方式を決めずに、設計に入る(推論: 要件の優先順位がなければ、トレードオフが選べない) |
| 切り戻しも含めて、停止時間を見積もる | 移行失敗時の切り戻しを、停止時間に含めない |
| 早めに、プロトコルの疎通と転送速度を確認する | 旧環境のネットワークを、確認せずに前提にする |
| セッション・ファイル・ログ・設定を、サーバーの外に出す | サーバーの中にセッションや一時ファイルを持つ(オートスケールと相性が悪い) |
| 複数のAZに配置し、ELBで分散する | 1つのAZだけで、冗長化なしで動かす |
| クエリを一括化して、AZ間の通信回数を減らす | 大量データを、1件ずつDBへ更新する |
| バックエンドサービスの呼び出しに、リトライとタイムアウトを設ける | タイムアウトなしで、長く待ち受ける |
| DBは、運用・コスト・保守性で選び、マネージドサービス化を必須で検討する | 現行踏襲だけで、同じDB製品を選ぶ |
| 製品固有機能を、同等・代替・廃止に仕分ける | 仕分けずに、スクリプトを持ち込む |
| 重い処理は、リソース増強の前に、DB分割・キャッシュ・キューを考える | 負荷が出たら、まずインスタンスを大きくする |
| 中間ファイルはS3に置き、キー名をDBに保管し、ライフサイクルで消す | 共有ファイルサーバーを、そのまま持ち込む(ミドルウェアの制約でやむを得ない場合を除く) |
| バッチは見直し、スケジューラーと実行環境を分けて選ぶ | バッチを単純移行して、リソースを浪費する |
| ページ通知を絞り、再発させない | 何でもページにして、運用者を疲弊させる |
| Rebuild/Replatform/Repurchase で検討する | Rehost(リフト&シフト)。ガバメントクラウドでは使えない |
| — | BYOL(ライセンスの持ち込み)。原則禁止 |

## 9. ガイドが書いていないこと(読んだ範囲)

- 方式の選び方は、フローチャートとコスト・リスク・負荷・期間の比較で示されているが、**具体的な停止時間の数値の基準**(何分以内ならリアルタイム同期、など)は書かれていない。
- Application Discovery Service の上限など、**AWS側の仕様に由来する数値**は、ガイドの作成時点のもの。最新の仕様は、書かれていない。
- 監視の通知の分類は「一例」で、ガイド自身が「すべてのシステムで最適とは限らない」と断っている。
- 推論: 第5節の可用性の表やDMSの要件は、2023年3月に作られた文書(改訂履歴)がもとなので、サービスの対応状況は変わっている可能性がある。使う前にAWSの最新ドキュメントで確認する。
